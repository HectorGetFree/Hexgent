# Hexgent 上下文管理设计

## 1. 设计目标

上下文管理负责控制一次会话持续增长的模型输入，在接近模型上下文窗口时压缩较早历史，同时保证：

- 完整会话记录不因压缩而丢失；
- 用户提交的每一条 Query 原文在 Transcript 中不可修改、不可压缩、不可删除；
- 活动上下文始终完整保留当前 Query，较早 Query 可以进入历史摘要；
- 当前 Plan 始终从 `PlanStore` 动态注入，不依赖历史摘要恢复；
- `function_call` 与对应的 `function_call_output` 不会被拆开；
- 压缩是 Agent Loop 中明确、可观测的状态迁移；
- 上下文容量限制与模型轮次、工具次数等运行预算相互独立。

本文档从上下文模块建立开始持续跟踪实际实现。后续修改上下文模块时，应同步更新对应章节。

## 2. 上下文分层

Hexgent 将上下文拆分为三层：

### 2.1 完整会话记录

`ConversationContext.transcript` 保存所有进入模型历史的完整内存记录。启用持久化的 CLI 会话还会通过 `SessionStore` 把用户 Query、Agent Run 边界、完整模型响应、工具执行状态、工具结果和压缩边界追加写入 JSONL。主动压缩不会删除这些记录。

Transcript 记录完整的逻辑事件，而不是逐字符保存流式 `delta`。流式文本在 `response.completed` 后以完整模型输出落盘，既能还原模型最终响应，也避免因渲染分片方式不同产生大量无意义记录。

每条 JSONL 记录的 `created_at` 使用带 `+08:00` 偏移的 `Asia/Shanghai` 北京时间，Session 目录前缀也使用同一时区生成。

持久化目录为：

```text
.hexgent/sessions/{YYYYMMDD-HHMMSS}_{首轮 Query 截断摘要}/
├── transcript.jsonl
└── tool-results/
```

`.hexgent/` 属于运行时数据，已加入 `.gitignore`。

会话目录在首轮 Query 到达时延迟创建。目录名称中的 Query 摘要会合并空白、过滤文件名非法字符并限制长度；同一秒发生重名时追加短随机标识。调用方仍可显式传入稳定 `session_id`，主要用于测试或后续恢复。

当前 JSONL 事件至少包括：

- `session_started`、`user_query`；
- `agent_run_started`、`agent_run_finished`；
- `model_response_completed`、`model_response_failed` 和完整响应消息；
- `tool_execution_started`、`tool_execution_finished`；
- `tool_result_persisted`、`context_compaction_boundary`。

大工具结果是 Transcript 的外置载荷，不是另一套会话记录。JSONL 保留原事件位置、`call_id`、状态和相对路径，`tool-results/` 保存不可截断的正文；二者共同构成可恢复的完整会话工件。

### 2.2 不可变用户 Query

`UserQuery` 是冻结数据对象，包含稳定序号和用户提交的原始文本。`ConversationContext` 使用内部追加式元组保存所有 Query，只允许通过 `append_user_query()` 新增。

Query 在 `active_messages` 中以 `UserQuery` 对象存在，调用模型前由 `model_messages()` 物化为原始 `user` 消息。所有 Query 永久保留在 `_user_queries` 和 Transcript；压缩时仅强制将最新 Query 原样留在活动上下文，较早 Query 可以进入摘要。

该分层保证审计记录不丢失，同时避免所有历史 Query 永久占据模型窗口。如果当前 Query 自身已经超过上下文硬上限，系统仍必须明确停止，不能截断或改写当前请求。

### 2.3 活动模型上下文

`ConversationContext.active_messages` 是下一次请求实际发送给模型的消息。压缩成功后，较早消息会被一条 `developer` 摘要替换，最近消息继续原样保留。

### 2.4 每轮运行时上下文

`context.builder.build_context()` 在每次模型调用前重新组合系统提示词和当前 Plan。工具定义也由请求现场提供。这些权威运行时信息不依赖压缩摘要。

## 3. 模块结构

```text
hexgent/context/
├── __init__.py       # 对外导出上下文主要类型
├── context.py        # 不可变 Query、完整记录和活动上下文
├── context_builder.py # 构建系统提示词和 Plan 上下文
├── context_budget.py # 上下文窗口及压缩阈值
├── session_store.py  # JSONL Transcript 与大工具结果持久化
└── compaction.py     # 选择安全边界并调用摘要模型

hexgent/utils/
└── token_estimator.py # 估算请求 Token
```

## 4. 状态所有权

CLI 会话通过 `ConversationContext.persistent(workdir)` 创建持久化上下文，并在多次用户输入之间复用。`LoopState` 引用该对象，因此同一次 Agent Run 的模型轮次和后续用户轮次共享相同上下文。

为了兼容原有调用方，`agent_loop()` 仍接受普通消息列表。普通列表会被包装为 `ConversationContext`，原列表作为完整记录继续接收后续消息。

`ConversationContext` 当前维护以下字段：

- `transcript`：不会被压缩删除的完整记录；
- `active_messages`：包含不可变 Query 和可压缩历史的活动条目；
- `round_boundaries`：完整 API 轮次结束位置；
- `compaction_count`：成功压缩次数；
- `consecutive_compaction_failures`：连续压缩失败次数；
- `partial_compaction_count`：当前连续流程已接受的部分有效压缩次数；
- `session_store`：可选的 JSONL 和工具结果持久化实现；
- `_user_queries`：只能追加的不可变 Query 元组。

## 5. 工具结果持久化

内置工具不再在 50,000 字符处直接截断结果。工具批次执行完成后，`SessionStore` 检查模型可见结果：

1. 单个结果超过 50,000 字符时写入 `tool-results/{调用摘要}__{call_id}.txt`；可读摘要经过非法字符过滤和长度限制，完整 `call_id` 继续保证唯一定位；
2. 单个结果均未超限，但批次内联结果合计超过 8,000 Token 时，从最大的结果开始外置，直到回到预算内；
3. `function_call_output` 使用 `<persisted-output>` 标记保存相对路径、原始字符数和预览；
4. 单个预览最多 500 字符，同一批次的预览合计最多约 4,000 Token；
5. 模型需要更多细节时可调用 `read_file` 读取持久化文件；
6. Transcript 追加 `tool_result_persisted` 记录。

工具调用对象和 `function_call_output` 仍保持原始 `call_id` 配对关系。

## 6. 压缩触发

`ContextLimits` 与 `LoopLimits` 分离。`LoopLimits.max_total_tokens` 控制一次运行的累计成本；`ContextLimits` 控制单次请求是否还能装入模型窗口。

普通运行参数通过工作区根目录的 `hexgent.toml` 统一加载。配置文件不存在或字段缺失时使用对应冻结数据类的代码默认值；未知配置段、未知字段、错误类型和非法数值会在启动时明确报错，避免拼写错误被静默忽略。

CLI 的 `--config` 可以选择其他 TOML 文件。仓库提供 `hexgent.compaction-test.toml` 用于单独验证上下文压缩：它关闭跨轮次的模型次数、工具次数、累计 Token 和总运行时间预算，并把主动压缩阈值降低到约 20,000 Token；单次模型输出上限及工具自身超时仍然保留。

配置加载只在进程入口发生一次，随后显式传递 `LoopLimits`、`ContextLimits` 和 `ToolResultLimits`。这些数据类不读取文件或环境变量，测试也可以直接构造配置对象。

主动压缩阈值为：

```text
context_window_tokens
- reserved_output_tokens
- safety_margin_tokens
```

当前默认值：

- 上下文窗口：128,000 Token；
- 正常输出预留：8,000 Token；
- 安全余量：8,000 Token；
- 摘要输出上限：2,000 Token；
- 压缩后近期消息目标：24,000 Token；
- API 拒绝过长请求后的应急近期消息目标：8,000 Token；
- 连续压缩失败上限：2 次。
- 最小有效收益：2,000 Token 或压缩前请求的 10%；
- 连续流程最多接受一次部分有效压缩。

第一阶段使用不依赖具体模型分词器的保守估算：ASCII 字符约按四个字符一个 Token，非 ASCII 字符约按一个字符一个 Token。请求估算同时包含 instructions、活动消息和工具定义。

## 7. 安全压缩边界

模型完整响应和其工具结果全部回填后，才记录一个 API 轮次边界。压缩切点只能选择这些边界，不能按消息数量直接截断。

```text
assistant function_call A
assistant function_call B
function_call_output A
function_call_output B
-------------------------- 完整轮次边界
```

这样可以保证工具调用和结果始终成对进入摘要或近期上下文。

压缩切点可以位于活动消息末尾，只要该位置是完整轮次边界。这允许在最新原子工具批次本身过大时，把整个已完成批次纳入摘要，而不是重复摘要旧摘要。

压缩后活动条目的排列为：

```text
最新不可变 UserQuery（若位于切点之前）
developer 历史摘要
最近的完整模型轮次
切点之后的近期消息
```

完整 `transcript` 不发生删除，并追加 `context_compaction_boundary`，记录摘要、覆盖消息数量、压缩前后 Token、摘要 Token、近期内容 Token 和压缩状态。

## 8. Agent Loop 集成

`run_turn()` 的顺序为：

1. 检查模型轮次、工具次数、累计 Token 和时间预算；
2. 构建当前系统提示词和 Plan 上下文；
3. 在正常工作轮或预算收尾轮调用主模型前检查活动上下文容量；
4. 如需压缩，最多进行两次结构化摘要尝试；
5. 验证候选摘要是否产生足够收益；
6. 完全有效或首次部分有效时提交上下文，并返回 `Continue(nextState, "context_compacted")`；
7. 下一轮使用压缩后的活动上下文调用主模型。

摘要模型调用不会产生 `TextDeltaEvent`，也不能调用工具。摘要必须是唯一的 `<summary>...</summary>` 区块，并按目标、约束、已完成、发现、状态、剩余工作和错误恢复组织；不得复制完整工具输出和旧最终报告。摘要消耗计入本次 Agent Run 的累计 Token，但不计入正常主模型轮数。

摘要 Prompt 明确禁止把内部压缩描述成任务中断、权限受限或 Agent 无法继续。摘要只是 Harness 的内部容量治理阶段；成功提交后，Agent Loop 会自动恢复原任务。

摘要能力不注册为模型可主动调用的普通工具。压缩触发条件、安全切点、收益验证、重试次数和状态提交均由 Harness 控制，避免模型自行压缩导致历史丢失或绕过容量策略。摘要模型调用是 Context 模块的内部能力，可供主动压缩和应急压缩共同复用。

`read_file` 在 `ToolExecutionContext` 中维护会话级内容 Hash 缓存。首次成功读取时记录绝对路径及完整内容的 SHA-256；后续读取仍会读取字节并重新计算 Hash，内容相同时只向模型返回 `<file-unchanged>` 占位符，内容变化时返回最新全文并更新缓存。该机制主要减少重复正文带来的 Context 开销，不以减少磁盘 I/O 为目标。

只有完整内联给模型的文件正文才允许继续命中缓存。单个结果或工具批次因预算而外置时，模型只看到预览和恢复路径，工具执行管线会清空读取缓存；外置失败时同样清空，避免后续错误地返回“文件未变化”却无法取得完整正文。

通用重复工具调用采用注册表声明的策略。第一版仅为 `glob` 启用 `exact`：参数通过解析、Schema 校验和权限检查后，工具名与排序后的规范化 JSON 参数形成 SHA-256 指纹；同一 Agent Run 内再次命中时不重复返回完整结果，而是返回包含首次 `source_call_id` 的 `<duplicate-tool-call>` 占位符。`read_file` 使用独立的 `content_aware` Hash 策略；`bash`、写入、编辑和 Plan 工具不复用调用结果。

每次 Agent Run 开始时清空精确调用缓存；`bash`、`write_file`、`edit_file` 成功执行后也会使其失效。去重调用仍生成当前 `call_id` 对应的 `function_call_output`，并计入工具预算；同一指纹重复达到三次时返回明确错误，防止模型依靠缓存命中形成循环。当前实现无法观察 Agent Run 期间由外部进程直接产生的文件系统变化，因此 `glob` 去重只适用于 Hexgent 自身工具可观测的执行边界。

主动压缩或应急压缩成功后会清空读取缓存和精确工具调用缓存。因为压缩可能使此前文件正文或工具结果离开活动上下文，清空后允许模型按需重新执行并取得完整结果，避免只收到去重占位符却无法访问原始内容。

## 9. 可观测事件

上下文模块向界面层发送：

- `ContextCompactionStartedEvent`：开始压缩，并携带压缩前估算值；
- `ContextCompactionFinishedEvent`：压缩成功，并携带前后估算值；
- `ContextCompactionFailedEvent`：压缩调用失败，并携带中文原因。

终端使用弱化样式展示这些事件，不输出内部摘要正文。

## 10. 失败处理

候选摘要只有在至少减少 2,000 Token 或 10%，且不会增加上下文时才允许提交。压缩后低于主动阈值为完全有效；仍高于主动阈值为部分有效，连续流程最多接受一次并立即进行更强压缩。

摘要格式错误、超出摘要预算或收益不足时会使用更严格提示有限重试。所有尝试失败时不修改活动上下文；低于硬阈值可以继续主模型，达到硬阈值则形成失败终态。

连续失败达到 `max_compaction_attempts` 后停止重复调用摘要模型，防止形成压缩失败循环。

如果 Token 估算低于阈值，但模型 API 仍返回 `prompt_too_long`、`context_length_exceeded` 等上下文过长错误，Agent Loop 会进入 Reactive Compact：

1. 记录本次模型失败及其可恢复原因；
2. 使用更小的 `reactive_recent_context_tokens` 强制执行一次安全压缩；
3. 产生 `Continue(nextState, "reactive_context_compacted")` 显式状态迁移；
4. 使用压缩后的上下文重新调用主模型；
5. 重试仍然返回上下文过长，或没有安全切点、摘要无效，则形成 `failed` 终态。

`LoopState.reactive_compaction_attempted` 保证一次 Agent Run 最多执行一次应急压缩和一次主模型重试，不会形成恢复死循环。当前 Query 自身过大且没有完整轮次可压缩时会直接失败，绝不截断或改写用户请求。

## 11. 当前实现边界

当前已经实现：

- 完整记录与活动上下文分离；
- 用户 Query 独立建模并在 Transcript 中冻结保存，活动上下文只强制保留最新 Query；
- JSONL Transcript 持久化；
- 完整 Agent Run、模型响应和工具执行事件持久化；
- 使用时间和首轮 Query 摘要生成可读会话目录；
- 大工具结果完整落盘并向模型提供路径和预览；
- 工具批次结果总预算和从最大结果开始的自适应外置；
- 上下文容量配置和 Token 估算；
- 按完整 API 轮次主动压缩；
- 支持将位于消息末尾的完整原子轮次纳入摘要；
- 结构化短摘要、压缩收益验证和单次部分压缩；
- 保留近期消息和最新用户输入；
- 每轮重新注入当前 Plan；
- 压缩状态事件和终端展示；
- 无效压缩有限重试和失败熔断；
- `prompt_too_long` 后最多一次 Reactive Compact 和主模型重试。

当前尚未实现：

- 手动 `/compact` 命令；
- Transcript 恢复加载和压缩状态恢复；
- Transcript 外置载荷校验和完整性清单；
- 旧工具结果 Microcompact；
- 确定性 Snip Compact；
- 使用模型原生 tokenizer 精确计数；
- 用户取消压缩；
- Web 入口的压缩事件协议。

## 12. 压缩结果状态

- `not_needed`：当前上下文未达到主动压缩阈值。
- `compacted`：压缩有效，且上下文已经回落到主动阈值以下。
- `partial`：压缩有效，但仍高于主动阈值，只允许有限次数续压缩。
- `failed`：本次压缩失败，但尚未达到必须停止的硬阈值。
- `blocked`：达到硬阈值且无法安全压缩，后续模型调用被阻止。
