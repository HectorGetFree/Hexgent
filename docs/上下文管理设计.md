# Hexgent 上下文管理设计

## 1. 设计目标

上下文管理负责控制一次会话持续增长的模型输入，在接近模型上下文窗口时压缩较早历史，同时保证：

- 完整会话记录不因压缩而丢失；
- 当前 Plan 始终从 `PlanStore` 动态注入，不依赖历史摘要恢复；
- `function_call` 与对应的 `function_call_output` 不会被拆开；
- 压缩是 Agent Loop 中明确、可观测的状态迁移；
- 上下文容量限制与模型轮次、工具次数等运行预算相互独立。

本文档从上下文模块建立开始持续跟踪实际实现。后续修改上下文模块时，应同步更新对应章节。

## 2. 上下文分层

Hexgent 将上下文拆分为三层：

### 2.1 完整会话记录

`ConversationContext.transcript` 保存完整会话记录。模型响应、工具结果、内部提醒和压缩边界都会进入该记录。主动压缩不会从中删除旧消息，为后续审计和持久化保留依据。

### 2.2 活动模型上下文

`ConversationContext.active_messages` 是下一次请求实际发送给模型的消息。压缩成功后，较早消息会被一条 `developer` 摘要替换，最近消息继续原样保留。

### 2.3 每轮运行时上下文

`context.builder.build_context()` 在每次模型调用前重新组合系统提示词和当前 Plan。工具定义也由请求现场提供。这些权威运行时信息不依赖压缩摘要。

## 3. 模块结构

```text
hexgent/context/
├── __init__.py       # 对外导出上下文主要类型
├── builder.py        # 构建系统提示词和 Plan 上下文
├── state.py          # 完整记录、活动消息和压缩元数据
├── limits.py         # 上下文窗口及压缩阈值
├── estimator.py      # 估算请求 Token
└── compaction.py     # 选择安全边界并调用摘要模型
```

## 4. 状态所有权

CLI 会话持有一个 `ConversationContext`，并在多次用户输入之间复用。`LoopState` 引用该对象，因此同一次 Agent Run 的模型轮次和后续用户轮次共享相同上下文。

为了兼容原有调用方，`agent_loop()` 仍接受普通消息列表。普通列表会被包装为 `ConversationContext`，原列表作为完整记录继续接收后续消息。

`ConversationContext` 当前维护以下字段：

- `transcript`：不会被压缩删除的完整记录；
- `active_messages`：实际发送给模型的活动消息；
- `round_boundaries`：完整 API 轮次结束位置；
- `compaction_count`：成功压缩次数；
- `consecutive_compaction_failures`：连续压缩失败次数。

## 5. 压缩触发

`ContextLimits` 与 `LoopLimits` 分离。`LoopLimits.max_total_tokens` 控制一次运行的累计成本；`ContextLimits` 控制单次请求是否还能装入模型窗口。

主动压缩阈值为：

```text
context_window_tokens
- reserved_output_tokens
- safety_margin_tokens
```

当前默认值：

- 上下文窗口：128,000 Token；
- 正常输出预留：8,000 Token；
- 安全余量：8,000 Token；
- 摘要输出上限：4,000 Token；
- 压缩后近期消息目标：24,000 Token；
- 连续压缩失败上限：2 次。

第一阶段使用不依赖具体模型分词器的保守估算：ASCII 字符约按四个字符一个 Token，非 ASCII 字符约按一个字符一个 Token。请求估算同时包含 instructions、活动消息和工具定义。

## 6. 安全压缩边界

模型完整响应和其工具结果全部回填后，才记录一个 API 轮次边界。压缩切点只能选择这些边界，不能按消息数量直接截断。

```text
assistant function_call A
assistant function_call B
function_call_output A
function_call_output B
-------------------------- 完整轮次边界
```

这样可以保证工具调用和结果始终成对进入摘要或近期上下文。

压缩后活动消息的排列为：

```text
developer 历史摘要
最近的完整模型轮次
最新用户消息
```

完整 `transcript` 不发生删除，并追加一条 `context_compaction_boundary` 记录本次摘要和覆盖的消息数量。

## 7. Agent Loop 集成

`run_turn()` 的顺序为：

1. 检查模型轮次、工具次数、累计 Token 和时间预算；
2. 构建当前系统提示词和 Plan 上下文；
3. 在正常工作轮或预算收尾轮调用主模型前检查活动上下文容量；
4. 如需压缩，执行摘要并返回 `Continue(nextState, "context_compacted")`；
5. 下一轮使用压缩后的活动上下文调用主模型。

摘要模型调用不会产生 `TextDeltaEvent`，也不能调用工具。它消耗的 Token 会进入本次 Agent Run 的累计 Token 预算，但不计入正常主模型轮数。

## 8. 可观测事件

上下文模块向界面层发送：

- `ContextCompactionStartedEvent`：开始压缩，并携带压缩前估算值；
- `ContextCompactionFinishedEvent`：压缩成功，并携带前后估算值；
- `ContextCompactionFailedEvent`：压缩调用失败，并携带中文原因。

终端使用弱化样式展示这些事件，不输出内部摘要正文。

## 9. 失败处理

压缩失败不会修改活动上下文。若当前估算值仍低于硬阈值，主模型可以继续执行；达到硬阈值时，本次运行形成失败终态，避免发送已知无法安全容纳的请求。

连续失败达到 `max_compaction_attempts` 后停止重复调用摘要模型，防止形成压缩失败循环。

## 10. 第一阶段边界

当前已经实现：

- 完整记录与活动上下文分离；
- 上下文容量配置和 Token 估算；
- 按完整 API 轮次主动压缩；
- 保留近期消息和最新用户输入；
- 每轮重新注入当前 Plan；
- 压缩状态事件和终端展示；
- 压缩失败次数限制。

当前尚未实现：

- 模型返回 `context_length_exceeded` 后的被动压缩恢复；
- 手动 `/compact` 命令；
- Transcript 和压缩状态持久化；
- 使用模型原生 tokenizer 精确计数；
- 用户取消压缩；
- Web 入口的压缩事件协议。
