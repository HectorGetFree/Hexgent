# 接口联调

目标是交付一套能实际执行、能解释结果、能判断是否触发目标代码的联调方案。

## 工作流程

### 1. 明确目标

先区分用户要验证的是：

- 接口自身能否成功；
- 某个内部调用链是否被执行；
- 某类异常是否能够稳定复现；
- 修复逻辑是否真正生效。

如果用户提到具体异常或方法，必须确认公开接口是否确实能到达该位置。名称相似不能作为链路证据。

### 2. 从源码还原链路

依次查找并核对：

1. 路由、HTTP 方法、请求结构和中间件；
2. API 层到 RPC 或 Service 层的参数映射；
3. 数据查询、配置读取和外部服务依赖；
4. PromptSymbol、工作流或模型调用位置；
5. 目标解析、修复或异常处理位置；
6. 异步任务、第二轮会话和延迟执行分支。

优先使用 `rg` 搜索路由、类型、错误日志原文和目标方法。结论中区分源码已确认事实与尚未验证的运行时条件。

搜索必须从具体服务目录、路由名或类型名开始。不要先执行全仓 `find`、`grep -R`，也不要把大段搜索结果直接返回给模型：每次先定位少量候选文件，再用带明确行号范围的 `sed` 或 `read_file` 精读。命令输出预计较大时，先增加路径、文件类型或关键词限制，必要时只保留前 200 行并说明截断原因。

### 3. 准备测试数据

根据真实查询条件生成只读 SQL，优先寻找已有数据，不直接插入或修改业务数据。SQL 应返回 curl 需要的字段，并标注字段与请求参数的对应关系。

注意以下约束：

- 数据所属用户应与 JWT 或 `noLogin` 中的用户一致；
- 枚举、课程、环节等值必须被当前代码配置支持；
- 涉及历史会话时，确认会话记录是否属于同一用户和业务；
- 空数据是否允许，要以源码分支为准。

只有用户明确要求且风险可控时，才提供写入型测试 SQL；执行前再次确认目标环境和数据范围。

### 4. 生成真实请求

HTTP 流式接口使用 `curl -N`；GET 参数优先使用 `-G --data-urlencode`，避免中文和特殊字符破坏请求。存在本地免登录能力时，先确认配置开关，再使用 `noLogin`；否则使用真实 Authorization。

RPC 接口优先提供 `grpcurl`，明确 proto 路径、服务方法和本地端口。

多轮会话必须拆成有顺序的请求：先创建会话并说明从哪里取得会话 ID，再携带 ID 发起下一轮。不要伪造一个未经验证的会话 ID。

### 5. 判断异常能否被触发

明确区分：

- **稳定触发链路**：请求满足条件后，目标方法一定执行；
- **概率触发异常**：目标方法会执行，但异常依赖模型随机输出或外部状态；
- **无法通过该接口触发**：公开接口根本不经过目标代码。

对于依赖模型产生坏 JSON 等随机条件的异常，不声称 curl 可以稳定复现。需要稳定复现时，建议使用固定模型响应、测试桩或目标方法测试，并说明这与真实接口联调的差异。

### 6. 给出观测点

至少提供以下一种证据：

- 应关注的关键日志文本；
- 预期响应中的关键字段或结束事件；
- 数据库或会话记录的只读核验 SQL；
- trace、PromptSymbol 或工作流名称。

如果目标逻辑是异步执行，明确说明 HTTP 请求完成不代表异步任务已经成功，并给出对应日志入口。

## 输出要求

回答保持简洁，通常按以下顺序组织：

1. 能否通过该接口触发目标链路；
2. 查询可用数据的 SQL；
3. 可直接执行的请求命令；
4. 多轮或异步触发步骤；
5. 预期结果、日志和稳定复现边界。

命令中使用清晰占位符，不展示配置文件中的密钥、Token 或数据库密码。
